# Blockchain Collector — Excel из трёх папок (локально)

Скрипт создаёт **одну приоритетную очередь Solana-адресов**, которые извлекаются
из разных категорий XLSX. Он запускается на ноутбуке, отдельный сервер не нужен.

| Папка | Тип | Приоритет | Интервал повторного сбора |
|---|---|---:|---|
| migrated | Мигрировавшие токены | 65 | 6 часов |
| trending | DEX Trending токены | 100 | 5 минут |
| wallets | Профитные кошельки | 90 | 15 минут |
| Из истории кошельков | Найденные swap-токены | 40 | 12 часов |

Эти категории — метки из Excel, а не on-chain подтверждение успешной миграции
или прибыльности кошелька. Адреса разных листов и файлов дедуплицируются.

## Установка

Откройте терминал в папке solana-launcher. Требуются Node.js, Python 3,
установленные npm зависимости. Команда: npm ci --legacy-peer-deps.

Добавьте HELIUS_API_KEY или HELIUS_API_KEYS в solana-launcher/.env.local.
Никогда не коммитьте реальные ключи. Импорт Excel и просмотр очереди доступны
без ключей Helius.

По умолчанию пути:

- data/seed-folders/migrated/
- data/seed-folders/trending/
- data/seed-folders/wallets/

Любые другие абсолютные пути можно указать через CLI.

## Проверка без изменения базы

Команда Windows PowerShell (в одну строку):

    node scripts/blockchain-seed-collector.cjs --mode import --dry-run --migrated-dir "D:\Crypto\Мигрировали" --trending-dir "D:\Crypto\DEX Trending" --wallets-dir "D:\Crypto\Профитные кошельки"

Проверьте в выводе missingFolders, skipped, matched и headerFound.
Для многостолбцовых файлов с неизвестными заголовками не угадываем, какой
адрес является mint: это может быть адрес торговой пары, а не токена.

## Импорт

    npm run blockchain:seeds -- --migrated-dir "D:\Crypto\Мигрировали" --trending-dir "D:\Crypto\DEX Trending" --wallets-dir "D:\Crypto\Профитные кошельки"

Повторно читаются только новые/изменённые файлы (размер + время модификации).
Поддерживаются вложенные папки и несколько листов одного XLSX.
Временные файлы Excel пропускаются. Исчезнувшие файлы по умолчанию не
удаляют собранную историю; ключ --prune-missing очищает только их seed-связи.

## Сбор с ограничением нагрузки

    npm run blockchain:collect -- --limit 100 --concurrency 2 --recent-limit 200 --backfill-limit 200

    npm run blockchain:status

    npm run blockchain:test

Параметр --limit задаёт число обрабатываемых адресов, а не транзакций.
Concurrency ограничен 1–4. При 429 снизьте concurrency или лимиты.
Скрипт выводит реальную скорость: targetsPerSecond и eventsPerSecond.

## Непрерывный сбор на ноутбуке

    npm run blockchain:watch -- --watch-interval 60 --limit 50 --concurrency 2

Каждую минуту проверяются Excel и очередь; после перезапуска процесс читает
сохранённые прогресс и курсоры из SQLite. Работает только при включённом
ноутбуке с запущенным процессом. Остановка Ctrl+C.
Аварийно оставленные leases автоматически истекают через 10 минут.

## Корректность

- Дедупликация по (kind,address) и (kind,address,signature).
- Отдельные курсоры для исторического backfill и пропущенных новых страниц.
- Сохранение сырых Helius транзакций как gzip-BLOB в локальной SQLite.
- Авторитетные доказательства сделок из истории КОШЕЛЬКОВ попадают в chain_forensic_activities.
- Legacy token_trades не пополняется наблюдениями только по mint: они не доказывают все сделки.
- Успешно обработанные задачи назначаются на следующий опрос по приоритету.
- Ошибки сохраняются с экспоненциальным backoff; не считаются успешным сбором.
- Токены, найденные в swap-истории прибыльных кошельков, добавляются в очередь.

## Важные ограничения

1. Новый pipeline предназначен для Solana. Ethereum/Bitcoin требуют
   отдельных декодеров Excel и RPC адаптеров.
2. Helius история адреса mint может быть неполной относительно всех swaps
   токена. Для подтверждения полноты нужен специализированный индексатор.
3. Текущая token_trades хранит только одну сделку на mint/signature. Отдельные
   операции внутри одной транзакции пока не выделяются instruction-index.
4. Без файлов пользователя заголовки и качество трёх XLSX типов не проверены.
5. Размер одного исходного события ограничен 512 KiB (до gzip); превышение
   приводит к ошибке, не к молчаливой потере данных.
6. Нет доказательств о реальном ускорении в X раз: фактическую пропускную
   способность нужно замерять с подключённым Helius на вашем ноутбуке.


## On-chain forensic analytics (15 октября 2026)

Excel используется только для извлечения адресов. Метки «мигрировал»,
«трендовый», «прибыльный» **не считаются фактами блокчейна**.

При сборе wallet применяется Helius Enhanced Transaction History с параметром
token-accounts=balanceChanged: учитывается активность связанных токен-аккаунтов.
При первом запуске новой версии прежние wallet backfill-курсоры сбрасываются:
старая выборка могла пропускать движения SPL. Повторная выборка расходует Helius
credits, но старые signature дедуплицируются в SQLite.

Команды (ноутбук, в папке solana-launcher):

    npm run blockchain:collect -- --limit 50 --concurrency 2
    npm run blockchain:forensics
    npm run blockchain:forensics -- --force --limit 1000
    npm run blockchain:status
    npm run blockchain:integration-test

После успешного сканирования wallet индекс обновляется из кэшированных
payload: новые signature декодируются инкрементально, а FIFO PnL
пересчитывается по уже индексированным событиям. Повторный forensic replay
**не делает HTTP-запросов**. Изменение версии декодера приводит к полному
локальному reindex, не к повторной загрузке Helius.

Таблицы:
- chain_seed_events: сырые Helius JSON в gzip с ключом (kind,address,signature).
- chain_forensic_activities: tx signature, slot, timestamp, wallet, mint, buy/sell/transfer/unpriced, quote в SOL, комиссия, индекс события.
- chain_forensic_edges: прямой SPL или SOL transfer между адресами, подпись транзакции; **не** доказательство общего владельца.
- chain_forensic_wallet_pnl: консервативная FIFO realised PnL в SOL либо SQL NULL + reasons.
- chain_forensic_wallet_sync: число обработанных raw events, версия алгоритма, coverage.

Подтверждённые priced сделки — только Helius events.swap с одним
приписываемым кошельку token leg, реальным количеством SOL/WSOL и подтверждённой
ролью кошелька в quote. «Largest transfer» не используется: он создавал
ложные buy/sell на переводах и агрегаторных транзакциях.

В chain_forensic_wallet_pnl:
- status='verified' и total_realized_pnl_sol заданы только когда история
  кошелька полная, нет разрывов, все проданные лоты имеют известную цену
  покупки и комиссия известна.
- status='unknown' и total_realized_pnl_sol IS NULL для неполной истории,
  входящего перевода без себестоимости, неразобранного свапа,
  неизвестного quote или комиссии и других неоднозначностей.
- known_realized_pnl_sol — отдельно подтверждённая **частичная** прибыль
  только по однозначно сведённым сделкам, не заменяет итоговой прибыли.
- Комиссия добавляется к стоимости покупки и вычитается из выручки продажи,
  когда кошелёк является fee payer. Jito tips, rent и внешние расходы
  могут мешать считать прибыль окончательной.
- Прибыль сделок в quote-активах, например USDC, не переводится в SOL по
  вымышленному курсу: операции остаются unpriced.

ВАЖНО: wallet index включает **только уже найденные/seeded кошельки**. Сам mint
не раскрывает всех исторических покупателей: scan по адресу mint нельзя
интерпретировать как полный token trade tape. Для всего рынка нужны потоки
DEX-программ / индексатор token accounts и отдельная проверка охвата.
Старые wallet_stats, wallet_token_stats, token_trades и UI пока остаются
legacy-аналитикой: не выдавайте их за проверенный forensic PnL до переключения API.

## Исправления по ревью PR #68

- Helius Enhanced REST передаёт курсор истории через параметр before-signature,
  а не before. Тест blockchain-helius-pagination.cjs покрывает 105 подписей,
  прерывание по известной подписи и историческое продолжение.
- Для оценённого swap проверяются accountData.tokenBalanceChanges
  (знак и количество mint на кошельке) и nativeBalanceChange: изменение
  нативного баланса должно согласовываться с котировкой и network fee.
  Отсутствие данных, расхождение, сложные fee legs, несколько внутренних
  swaps и неизвестное количество токена создают unpriced evidence.
- Декодированные события типа UNKNOWN, если невозможно проверить балансы,
  и SWAP без распознанных действий блокируют окончательную PnL-оценку.
- Кэшированные метаданные различают техническое окончание пагинации Helius
  и полноту доказательств. Нельзя получить true из кэша, если evidence
  помечен incomplete. Миграция старой SQLite-таблицы аддитивная.
- Не допускается молчаливая потеря новых токенов после 25-го результата.
- Прогон blockchain-collector-forensics-integration.cjs проверяет 31 mint,
  инкрементальное чтение и дедупликацию SQLite.

СЛЕДУЮЩИЙ СЛОЙ: полный торговый tape для **всех кошельков**, а не только
seeded wallet, потребует индексатора событий DEX-программ. Новая схема сейчас
покрывает только наблюдаемые seeded кошельки. Любое утверждение о числе ВСЕХ
покупателей, ПОЛНОЙ истории токена или полном PnL всех трейдеров невалидно.

Проверка на реальных Helius-запросах и исторических XLSX обязательна
перед демонстрацией данных как полностью подтверждённых.


## DEX-наблюдения по данным блокчейна (PR #68, дополнительный слой)

Дополнительный индексатор DEX работает **локально на ноутбуке**, используя
существующую очередь Helius, SQLite и gzip-кэш. Это не облачный сервер.
Он ничего не считывает из Excel как доказательство сделок.

### Настройка

В solana-launcher/.env.local добавьте строку:

    CHAIN_DEX_PROGRAM_IDS=6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P,pAMMBay6oceH9fJKBRHGP5D4bD4sWpmSwMn52FMfXEA

В этом примере — официальные идентификаторы программ Pump.fun и PumpSwap.
Они указаны в документации проекта pump-fun/pump-public-docs и SDK.
Другой официальный пример для Orca Whirlpools:
whirLbMiicVdio4qvUfM5KAg6Ct8VwpYzGff3uctyCc.
Используйте только реальные 32-байтные base58 **адреса программ DEX**,
проверенные в официальных источниках. Адреса токенов, пулов и кошельков
не заменяют адресов программ. Можно указать не более 8 программ; без настройки
DEX-сканирование полностью отключено, чтобы не расходовать Helius кредиты.

Затем из директории solana-launcher:

    npm run blockchain:collect -- --limit 2 --concurrency 1 --recent-limit 100 --backfill-limit 100
    npm run blockchain:status
    npm run blockchain:dex-replay -- --limit 10000

Обычный сбор **не запрашивает историю адреса mint**: она не раскрывает
полный поток сделок, но расходует Helius credits. Для диагностики прямого
трафика mint есть явный флаг `--scan-mint-addresses`; результаты такой
диагностики не превращаются в подтверждённые рыночные сделки.

Программа DEX добавляется в ту же очередь с собственными курсорами backfill и
catch-up. Для активных DEX это **много** транзакций, сканирование необходимо
запускать дозированно и следить за расходом кредитов. Последняя команда
только переиндексирует уже полученные программные Helius транзакции из SQLite
без дополнительных запросов к сети.

Таблицы chain_dex_observed_trades и chain_dex_indexed_signatures отделены
от FIFO PnL кошельков. Индекс принимает лишь swaps с однозначным SOL/WSOL quote,
конкретным владельцем токенового баланса, согласованным token/native
balanceChange и без неразрешённых дополнительных комиссий. Наблюдения
дедуплицируются в пределах одной программы, а API дополнительно убирает
дубликаты одной сделки, замеченной несколькими программами.

### Просмотр результатов

- GET /api/blockchain/evidence?mint=SOLANA_MINT — наблюдаемые DEX-сделки,
  сделки seeded-кошельков и их подтверждённый либо неизвестный PnL.
- GET /api/blockchain/evidence?wallet=SOLANA_WALLET — локальные операции,
  реальные переводы, сводка количества считанных транзакций, отдельные PnL.
- В интерфейсе /trade/analysis/evidence — вкладка «Проверенные данные».
  Основная вкладка анализа помечена «On-chain · оценка»: её старые
  показатели не считаются подтверждённым FIFO и не смешиваются с доказательствами.

Индекс наблюдений **не подтверждает** всех покупателей и продавцов токена:
можно пропустить программу, историю или транзакцию с неизвестным форматом.
Поля globallyComplete=false и verifiedGlobalPnl=false всегда выставляются
явно. Перевод между адресами не означает одного владельца. История сделок
от стороннего API без полной себестоимости не доказывает реализованную прибыль.

Helius Enhanced REST /v0 остаётся основой текущего legacy-слоя. Helius
выпустил Parsed Events API как его преемника; переход требует отдельного
адаптера формата и тестирования на реальных ответах. Live API-запросы в PR
не выполнялись, ключи в исходниках не сохранялись.


## Надёжность SQLite и устранение ошибок PR #68

**Одна база данных**: веб-приложение и консольный сборщик должны выполняться
в одном локальном файловом окружении. Оба по умолчанию используют
solana-launcher/data/trade.db. При необходимости задайте одинаковое абсолютное
расположение в .env.local и у процессов Next.js / коллектора:

    SOLANA_TRADE_DB_PATH=C:\solana-data\trade.db

Обратите внимание: если Next.js работает на удалённом хосте, он **не может**
открыть файл на ноутбуке по такому пути. Отдельный удалённый SQLite-сервер
здесь не предполагается.

**Проверка и резервная копия (рекомендуется до обновления):**

    npm run blockchain:db-check
    npm run blockchain:db-backup

Снимок создаётся через SQLite Online Backup API с учётом WAL и проходит
integrity_check. Он размещается рядом с исходной базой в директории
sqlite-backups. Для полноценной защиты храните копию также на другом
физическом диске; локальная папка на том же диске не защищает от его отказа.
Не делайте обычный cp работающего файла .db в режиме WAL.

Что гарантирует новый механизм:
- каждая аренда коллектора имеет lease_token; старый процесс не вправе
  перезаписать курсор после перехода аренды к другому процессу;
- первичные транзакции, состояние задания и производные индексы одного
  прохода фиксируются атомарно; исключение откатывает весь SQLite commit;
- Helius payload сохраняется с SHA-256 и raw_revision; изменившийся
  документ с той же подписью переиндексируется без дублирования;
- forensic-кэш учитывает сумму raw_revision, а DEX-кэш хранит хеш
  оригинального JSON и decode_status; неполная декодировка отмечается;
- повторный DEX replay выбирает ещё не обработанные или устаревшие
  транзакции вместо повторения постоянного окна последних 10 000;
- повторный forensic replay отдаёт приоритет ещё не анализированным
  кошелькам;
- кэш старой таблицы /api/database/wallets получает durable revision
  через SQLite-триггеры при INSERT, UPDATE и DELETE исходных таблиц.
  Инициализация схемы выполняется один раз за запуск модуля Next.js;
- /api/blockchain/evidence использует ограниченную выборку и лимит запросов.

Что ещё требует оценки на живых данных: рост базы и WAL, производительность
полного FIFO пересчёта на очень больших кошельках, нагрузка от локальных
триггеров при массовой записи, восстановление после отключения питания и
совместимость с реальными ответами Helius. Эти проверки не заменяются CI.
Legacy token_trades имеет исторический PRIMARY KEY(mint,signature) и может
агрегировать несколько fill одной транзакции; для доказательной аналитики
используются **отдельные** forensic/DEX таблицы, а не устаревший rollup.

Запуск проверки функциональности на локальном SQLite без сетевых расходов:

    npm run blockchain:integration-test

Отдельный CI регрессионный набор проверяет миграцию старой SQLite, атомарный
rollback, потерю аренды, обновление source revision, WAL backup и DEX replay.


## Множественные исполнения и потоковый FIFO (PR #68, обновление)

Legacy-таблица token_trades сохраняет исходный PRIMARY KEY(mint,signature):
существующие записи НЕ переносятся и НЕ удаляются. Для источников,
которые действительно знают стабильный порядковый индекс исполнения,
добавлена token_trade_fills с ключом (mint,signature,leg_index).

Вызов persistTokenTrades(mint, rows) с явным целочисленным legIndex
пишет отдельное исполнение; повторная запись той же тройки обновляет запись
без дублирования. Старые вызовы без legIndex продолжают использовать
историческую таблицу. getTokenTrades, listRecentTokenTrades и
/api/database/wallets читают объединение: если для подписи есть
индексированные исполнения, её старая агрегированная запись подавляется.
Это предотвращает двойной подсчёт, не переписывая пользовательскую базу.

ВАЖНО: текущий эвристический txsToTrades на основе старого Helius Enhanced
по-прежнему выдаёт максимум одну legacy-запись на подпись. Нельзя
выдумывать legIndex, если источник не раскрывает идентификаторы исполнений.
Поэтому таблица token_trade_fills поддерживает будущие точные источники,
но сама по себе не доказывает полный поток рыночных сделок. Для
доказательных on-chain наблюдений по-прежнему используйте отдельные
chain_dex_observed_trades и chain_forensic_activities.

Перерасчёт wallet FIFO больше не загружает всю историю транзакций в JS-массив:
gzip-кэш читается порциями по 200 подпечатанных событий в порядке подписи.
Затем по упорядоченному SQLite-курсору вычисляется FIFO, сохраняя в памяти
главным образом незакрытые лоты и сводки по токенам. Индекс
idx_forensic_fifo_stream уменьшает потребность во временной сортировке
по всей истории кошелька. Полный replay выполняется внутри SQLite
транзакции и не публикует частично пересчитанный PnL.

Проверки: blockchain-token-trade-fills-regression.cjs моделирует обновление
существующей базы и два исполнения одной подписи; core-регрессия
сравнивает потоковый расчёт со старым на пограничных сценариях и проходит
по 40 000 событиям; blockchain-forensics-stream-sqlite-regression.cjs
проверяет 3000 gzip-событий и план индекса. Это синтетические тесты,
**не нагрузочный прогон реального mainnet / не проверка вашей базы на ноутбуке**.

Перед обновлением локальной базы:

    npm run blockchain:db-check
    npm run blockchain:db-backup
    npm run blockchain:integration-test


## Пилот рекурсивного сбора одного токена и бюджет Helius

Пилот запускается отдельно от Excel-источников и не импортирует остальные seed-листы:

    npm run blockchain:pilot -- --seed-token 5XaxQZGNEAPvF34iYHuTgfLBzpRGg1spPYeGSzr5pump --monthly-credits-used 0 --pilot-budget-credits 1000000

Замените `0` на фактические использованные кредиты из Helius Dashboard за текущий billing period. Оставляйте `0` только если Dashboard действительно показывает нулевое использование.

Начальные ограничения по умолчанию:
- месячный локальный лимит: 10 000 000 расчётных кредитов;
- накопительный лимит одного пилотного scope на все запуски и возобновления: 1 000 000 расчётных кредитов;
- лимит одного запуска: 250 000 расчётных кредитов;
- оценка одной HTTP-страницы Enhanced Transactions: 110 кредитов;
- максимум объектов, обрабатываемых за запуск: 10 000;
- максимальная длительность запуска: 6 часов (активные запросы завершаются и фиксируют курсоры);
- активная волна токенов одного создателя: 200;
- активная волна кошельков одного токена: 5 000;
- активная волна кандидатов-создателей от одного кошелька: 20;
- concurrency: 2.

Эти ограничения управляют размером активной волны, а не удаляют найденные объекты.
Неактивированные кандидаты хранятся в постоянной таблице отложенной очереди и
продвигаются по мере завершения предыдущей волны. Состояние волны восстанавливается
из SQLite после перезапуска. Флаги настройки: `--max-runtime-ms`,
`--creator-wave-tokens`, `--token-wave-wallets`, `--wallet-wave-creators`.

Настройки можно переопределить CLI-флагами или переменными окружения:
- \`--monthly-budget-credits\` / \`HELIUS_MONTHLY_BUDGET_CREDITS\`;
- \`--monthly-credits-used\` / \`HELIUS_MONTHLY_CREDITS_USED_BASELINE\` — credits already used in the current provider billing period before local tracking began;
- \`--budget-period-start-day\` / \`HELIUS_BUDGET_PERIOD_START_DAY\` — UTC day-of-month when your Helius monthly period resets (default 1);
- \`--run-budget-credits\` / \`HELIUS_RUN_BUDGET_CREDITS\`;
- --pilot-budget-credits / HELIUS_PILOT_BUDGET_CREDITS — накопительный лимит scope; увеличивать только после проверки доступной квоты.
- \`--page-credit-estimate\` / \`HELIUS_ADDRESS_TX_ESTIMATED_CREDITS_PER_REQUEST\`;
- \`--limit\`, \`--max-objects\`, \`--concurrency\`.

Каждый сетевой запрос резервирует оценку в SQLite до отправки. Ответные заголовки
с фактическим расходом записываются, если провайдер их предоставляет; иначе
для guard используется оценка. Неуспешные попытки остаются в журнале и тоже
учитываются по оценке, так как нельзя доказать, что они были бесплатными.
Порог проверяется атомарно между worker-процессами. До первого сетевого запуска обязательно задайте \`--monthly-credits-used\` по Helius Dashboard: это кредиты, уже потраченные в текущем billing period до включения локального журнала. Baseline не должен включать запросы, уже записанные локальным журналом. \`--budget-period-start-day\` должен совпадать с днём сброса квоты (например, \`16\` для периода с 16-го числа); после начала нового периода установите baseline в \`0\`. Без явного baseline сетевой режим завершается до запроса, чтобы не считать ранее потраченные кредиты бесплатными. Когда достигнут run-, pilot- или monthly-лимит,
новые запросы блокируются, очередь и курсоры сохраняются, а уже полученные
страницы коммитятся вместе с курсором. Pilot-лимит считается по всем запускам
конкретного scope, а не сбрасывается при перезапуске. Увеличить его можно
явным флагом --pilot-budget-credits; месячный лимит увеличивайте отдельно
только после проверки новой квоты Helius. Следующий запуск продолжает задачу.

**Важно:** 110 кредитов на страницу — настраиваемая локальная оценка, а не
утверждение о фактической цене Enhanced Transactions endpoint и не точный
счётчик биллинга Helius. Сверяйте расход с Dashboard; если заголовки фактических
кредитов отсутствуют, задайте более консервативную оценку. Текущий период
учёта — календарный месяц UTC, он может не совпадать с датой сброса квоты
вашего аккаунта. Месячный guard контролирует только запросы, прошедшие через
этот локальный collector, а не другие приложения с тем же API key.

Статус и текущий учёт можно посмотреть так:

    npm run blockchain:status

Пилот использует отдельный scope \`seed-token:<mint>\`: объекты из Excel и другие
источники не будут взяты этим запуском. Очередь хранит приоритет, причину
обнаружения и исходную сущность. В первой итерации включено обнаружение
участников из доступной mint-address истории и рекурсивное расширение по
кошелькам/токенам/создателям. Для Pump.fun creator принимается только при наличии
успешной Enhanced-транзакции с источником `PUMP_FUN`, типом `CREATE` или
`TOKEN_MINT` и инструкции с точным Pump.fun program ID; адрес создателя берётся
из аккаунтов инструкции, а не из `feePayer`. Найденные запуски сохраняются в
`chain_pumpfun_creator_launches`, остальные токены создателя идут через
отложенную приоритетную очередь.

Это ещё не полный индекс торгов/переводов: история адреса mint **не доказывает
полную историю всех сделок и переводов токена**. Отдельный полный transfer-history
адаптер и универсальный DEX trade tape не подключены; если launch transaction
не раскрывает ожидаемую структуру инструкции, creator остаётся неизвестным.
`possibleGap=1` для токенов и истории запусков создателя сохраняется намеренно, пока полнота соответствующих декодеров не подтверждена. Не считайте такой запуск полным графом токена или основанием для \`verified\` PnL.

Локальные тесты бюджета и возобновления:

    node scripts/blockchain-seed-budget-regression.cjs
    node scripts/blockchain-recursive-pilot-regression.cjs
    node scripts/blockchain-helius-pagination.cjs
