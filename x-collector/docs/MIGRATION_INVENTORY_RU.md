# Аудит миграций X Collector

## Правило

Порядок применения SQL задаётся только `lib/trade/migrations.ts` и сохраняемым
именем в `schema_migrations`. Исторические коллизии номеров `012`, `013`,
`014` и `036` не переименовываются автоматически: существующая БД уже
может содержать эти имена. Переименование без совместимого перехода может
заставить старую БД повторно выполнить DDL.

В каталоге также есть восемь SQL-файлов, которые намеренно не входят в
`REQUIRED`. Они явно перечислены в `EXCLUDED_MIGRATIONS` с причиной.
Это предотвращает случайный запуск SQL «просто потому, что файл лежит в
migrations/`.

## Контроль

`npm run migrate:audit` выполняет файловый preflight без подключения к
PostgreSQL. Обычный `npm run migrate` выполняет тот же preflight **до**
создания Pool.

Добавление нового SQL требует сначала добавить его в явный manifest либо
в список исключений с обоснованием. Неизвестный SQL блокирует мигратор.

## Контрольные суммы применённых миграций

Мигратор сохраняет SHA-256 SQL в `schema_migrations.checksum`. Перед любыми
изменениями проверяются все применённые файлы; несовпадение или неизвестная
запись останавливают запуск. Исправляйте исходный файл, а новую схему меняйте
отдельной миграцией. Переводы строк CRLF/LF нормализуются для Windows/Linux.
Хеш описывает исходный SQL, а не фактическую схему: ручные ALTER TABLE этим
механизмом не обнаруживаются.

`npm run migrate -- --status` ничего не изменяет и показывает `[unverified]`
для старых записей без хеша. Обычный запуск с такими записями блокируется.
После сверки SQL с версией, применённой при развёртывании, и резервной копией
оператор явно выполняет `npm run migrate -- --baseline-checksums`, затем
обычный `npm run migrate`. Baseline записывает только отсутствующие хеши,
не выполняет ожидающие SQL и не перезаписывает известные хеши. Он фиксирует
текущую сверенную версию, но не доказывает задним числом, какой SQL выполнялся.

## 046_tweet_token_linker.sql

Миграция добавляет к `tweet_token_links` способ сопоставления, уровень уверенности, confidence и JSONB-доказательство. Существующие связи от контекстных задач сохраняются как `task_context` / `probable` с нейтральным confidence `0.5`; это эвристический вес, не калиброванная вероятность и не точное упоминание токена. Дополнительно миграция исправляет `rebuild_author_lead_stats()`: результат `AVG(double precision)` приводится к `NUMERIC` перед `ROUND`, поскольку PostgreSQL не поддерживает `ROUND(double precision, integer)`.

`tweet_token_linker_state` хранит идемпотентный прогресс отдельного процесса. Команда `npm run link:tweet-tokens` проверяет точные Solana-адреса в тексте твита и создаёт связь только если адрес присутствует в `archive_tokens` или в реестре `ip_entities` типа `TOKEN` для Solana. Символы/тикеры без адреса в первой версии автоматически не связываются, чтобы не создавать ложные совпадения.

## 047_signal_quality_marts.sql

Миграция добавляет `signal_quality_outcomes`, `v_signal_quality_mart`, `v_signal_quality_summary` и `v_signal_quality_by_mint`. Последняя витрина позволяет разбирать coverage и качество будущего attention outcome по конкретному mint. Это отдельная витрина результатов исторических сигналов, использующая `signal_history` и `mint_attention_snapshots`; существующий `backtest_runs` не переопределяется.

`refresh_signal_quality_outcomes(from, to, horizons)` связывает сигнал с последним снимком не старше часа до сигнала и снимком в фиксированном будущем окне `[signal + horizon, signal + horizon + 1h)`. Для входного baseline требуется не менее 100 агрегированных просмотров. Статусы `pending`, `missing_entry`, `missing_exit` и `low_baseline` сохраняются явно, а не превращаются в нулевой результат.

Запуск: `npm run signal:quality -- --source early_signal --horizon-hours 6 --lookback-days 90 --threshold 60 --min-samples 20`. Можно задать `--split-at 2026-09-15T00:00:00Z`; иначе окно автоматически делится хронологически 70/30. Порог должен быть выбран по train-части и оставлен неизменным для out-of-sample test. Команда показывает выбранную группу (`score >= threshold`) и baseline (`score < threshold`), coverage, среднее/медиану изменения просмотров и долю положительных исходов. Для программного доступа из аналитического слоя добавлены `getSignalQualityMart`, `getSignalQualitySummary` и `getSignalQualityByMint` в `lib/trade/analytics.ts`.

**Ограничение метрики:** это изменение суммарных просмотров в собранном наборе твитов, не полная активность X, не цена токена, не доходность и не P&L. Без достаточного количества готовых наблюдений команда завершится с кодом 2 и сообщит, каких выборок не хватает. Результаты с разной полнотой сбора нельзя честно сравнивать без проверки coverage.

## 048_signal_registry_versions.sql

Миграция закрепляет версии определений и порогов сигналов и делает временные окна оценки явными.

- `signal_registry` хранит ключ сигнала, версию, описание, baseline window, длительность outcome window и минимальный baseline просмотров.
- `signal_thresholds` хранит историю порогов с `threshold_version`, интервалом действия и единственным default-порогом на версию сигнала.
- `signal_history.signal_version` и `signal_quality_outcomes.signal_version` разделяют версии сигнала; версия включена в ключи, поэтому результаты разных версий не перезаписывают друг друга.
- `signal_quality_outcomes` хранит `baseline_window_start/end` и `outcome_window_start/end` отдельными полями. Функция `refresh_signal_quality_outcomes()` использует параметры из реестра и обновляет строку только при изменении аналитического результата.
- `v_signal_quality_by_author` связывает готовые результаты с авторами, у которых есть exact/confirmed mint-связь в baseline-окне. Это описательная атрибуция: один исход может относиться к нескольким авторам, поэтому строки витрины не являются независимыми наблюдениями.
- Пересчёт сохраняет прежний `evaluated_at`, если аналитические поля не изменились; поэтому результат повторного расчёта детерминирован по содержимому.
- `npm run signal:quality` теперь принимает `--signal-version` и `--threshold-version`. Без `--threshold` используется default из реестра; явный `--threshold` — непостоянный CLI override, который выводится в отчёте и не записывается в БД.

Исторические строки получают версию 1 и окна, соответствующие прежней логике: baseline до 1 часа перед сигналом, outcome начинается через заданный горизонт и длится 1 час. Существующие пороги мигрируются из legacy-правил: hype=60, ultra=70, early_signal=60; для entity начальный порог установлен в 60.

## 049_raw_retention_author_id.sql

Миграция добавляет к `archive_raw_pages` явные `parser_version`, `parse_status`, `response_status` и `expires_at`. Существующий `hash` — SHA-256 полного capture-файла/конверта; `response_hash` отдельно хеширует именно `source_response` (или весь объект, если отдельного поля ответа нет), чтобы находить повторяющиеся ответы без схлопывания разных наблюдений.

- `parse_status`: `captured / parsed / partial / failed`.
- `response_status`: `unknown / empty / nonempty / error`; пустая выдача отделена от ошибки парсинга.
- `expires_at`: существующие raw-файлы получают срок 90 дней от `received_at`; новые записи используют `ARCHIVE_RAW_RETENTION_DAYS` (по умолчанию 90, допустимо 1–3650).
- `npm run xactions:archive-gc` работает в dry-run; удаление истёкших файлов и метаданных выполняется только с `--delete`. Файл сохраняется, если на него ссылается хотя бы одна неистёкшая запись.
- `twitter_tweets.author_id` — nullable TEXT; ID не преобразуется в JS number. Существующие значения подтягиваются из `archive_posts`, если они доступны.
- `v_twitter_tweet_metrics_history` — аналитический интерфейс к уже существующей истории `archive_metrics`; отдельная дублирующая таблица снимков метрик не создаётся. В представлении отдельно доступны время получения и время, к которому относятся метрики.

## Безопасное упорядочивание в будущем


Если потребуется перейти на монотонные номера, сначала нужна отдельная
совместимая миграция/реестр с тестами для существующих production БД.
Исторические файлы нельзя просто переименовать и считать проблему решённой.
