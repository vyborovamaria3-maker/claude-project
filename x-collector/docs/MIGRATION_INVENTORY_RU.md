# Аудит миграций X Collector

## Правило

Порядок применения SQL задаётся только `lib/trade/migrations.ts` и сохраняемым
именем в `schema_migrations`. Исторические коллизии номеров `012`, `013`,
`014` и `036` не переименовываются автоматически: существующая БД уже
может содержать эти имена. Переименование без совместимого перехода может
заставить старую БД повторно выполнить DDL.

В каталоге также есть восемь SQL-файлов, которые намеренно не входят в
`REQUIRED`. Они явно перечислены в `EXCLUDED_MIGRATIONS` с причиной.
Это предотвращает случайный запуск SQL «просто потому, что файл лежит в
migrations/`.

## Контроль

`npm run migrate:audit` выполняет файловый preflight без подключения к
PostgreSQL. Обычный `npm run migrate` выполняет тот же preflight **до**
создания Pool.

Добавление нового SQL требует сначала добавить его в явный manifest либо
в список исключений с обоснованием. Неизвестный SQL блокирует мигратор.

## 046_tweet_token_linker.sql

Миграция добавляет к `tweet_token_links` способ сопоставления, уровень уверенности, confidence и JSONB-доказательство. Существующие связи от контекстных задач сохраняются как `task_context` / `probable` с нейтральным confidence `0.5`; это эвристический вес, не калиброванная вероятность и не точное упоминание токена.

`tweet_token_linker_state` хранит идемпотентный прогресс отдельного процесса. Команда `npm run link:tweet-tokens` проверяет точные Solana-адреса в тексте твита и создаёт связь только если адрес присутствует в `archive_tokens` или в реестре `ip_entities` типа `TOKEN` для Solana. Символы/тикеры без адреса в первой версии автоматически не связываются, чтобы не создавать ложные совпадения.

## Безопасное упорядочивание в будущем

Если потребуется перейти на монотонные номера, сначала нужна отдельная
совместимая миграция/реестр с тестами для существующих production БД.
Исторические файлы нельзя просто переименовать и считать проблему решённой.
