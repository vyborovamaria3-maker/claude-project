# X Collector: локальная надёжность и полнота (Windows)

Изменения рассчитаны на запуск на ноутбуке. Отдельного сервера не нужно.

## Перед запуском

1. Остановить локальные процессы сборщика и сохранить текущий PostgreSQL.
2. Выполнить `npm ci` и `npm run migrate`. Обязательные новые миграции:
   `044_browser_checkpoints.sql` и `045_collector_trace.sql`.
3. Выполнить `npm run typecheck && npm test && npm run build`.
4. Проверить реальный тестовый аккаунт X и резервную копию отдельно:
   автономный CI **не** является проверкой реальной сессии и SOCKS5.

## Браузерный checkpoint

После успешного сохранения пакета публикаций PostgreSQL в той же
транзакции фиксирует количество **новых task-post ссылок** и крайние ID.
Перед повторной попыткой проверяется отпечаток исходного задания.
Сохраняется один task checkpoint с состояниями:

- `partial` — часть данных уже сохранена, задание ещё не завершено;
- `unverified` — ограниченный сбор завершился, полнота X неизвестна;
- `target_reached` — выполнено целевое количество записей; **это не**
  подтверждение конца выдачи X.

По умолчанию повторный браузерный проход безопасно перечитывает выдачу,
а существующие task-post ссылки не дублируются. Это восстановление
**прогресса хранения**, а не гарантированный HTTP/DOM-cursor X.
Опциональное `X_BROWSER_RESUME_CURSOR=true` позволяет дописать
`max_id` в поисках `latest` при отсутствии исторических, list и
других курсоров. Включать только на тестовой учётной записи после
проверки порядка выдачи X: сортировка/репосты могут сделать такую
оптимизацию неполной. Для timeline надёжного курсора нет.

## Квоты

Первый вызов браузера и XActions оплачивается общей резервацией
`pickAccount`. Последующие браузерные прокрутки (консервативно)
или HTTP-вызовы XActions резервируют новую операцию в
`x_accounts` под lease аккаунта. Если квота закончилась,
задача ожидает следующего окна; ограничение не обходится.

## Повторные задачи

`enqueueWindowedTask` в `src/collector/queue` задаёт стабильный
`idempotency_key` из источника, цели, параметров и явного UTC окна.
Дубликат одного окна возвращает существующий ID; новое окно может
быть поставлено отдельно. У существующих планировщиков сохраняется
их собственная checkpoint-механика.

## Диагностика и контроль качества

- `npm run x:errors` — последние ошибки с безопасными кодами.
- `npm run x:quality` — отчёт за 24 часа по состояниям браузерных
  checkpoint. `target_reached` не означает полное покрытие X.
- Детали задания возвращают последние до 100 событий `xc_task_events`
  (этап, воркер, аккаунт, количество; без cookie, текста и URL).
- Для расследования сбоя смотрите `task_id`, `attempt`, `stage`,
  `created_at`. Запись событий best-effort, не является аудитом каждого
  пакета; неуспешный PostgreSQL-запрос не обязан оставлять event.

## Резервные копии на Windows

Заполнить `.env` (`DATABASE_URL`). Установить PostgreSQL client tools,
убедиться, что `pg_dump` и `pg_restore` присутствуют в PATH.

```powershell
npm run db:backup:windows
```

Команда сохраняет пользовательскую БД в `x-collector/backups/*.dump`,
проверяет, что формат custom читается `pg_restore --list`, атомарно
переименовывает временный файл и хранит последние 7 копий. Пароли не
передаются в командной строке; каталог `backups/` исключён из Git.
Файлы содержат конфиденциальные данные даже при зашифрованных сессиях —
защитите учётную запись Windows и диск. `pg_restore --list` проверяет
метаданные, **не заменяет** восстановление в отдельную тестовую БД.
Периодический запуск можно установить в Планировщике заданий Windows
вручную (только с явного разрешения владельца ноутбука):

```powershell
npm run db:backup:schedule:windows
# или свое локальное время, например:
npm run db:backup:schedule:windows -- -At 04:00
```

Это зарегистрирует `XCollectorPostgresBackup` ежедневно в 03:00 по
локальному времени Windows (или в выбранное время). Для запуска нужны
права на создание пользовательского запланированного задания и доступный
`node.exe` в PATH. При спящем ноутбуке задача начнётся, когда
Планировщик сможет её запустить; это не гарантирует точный запуск во
время сна. Проверяйте LastTaskResult в Планировщике заданий.

## Границы проверки

Рекомендуется тест: убить браузер после сохранённого пакета, восстановить
worker, убедиться, что уже записанные task-post links не удваиваются;
затем остановить службу PostgreSQL, проверить DEGRADED/READY и
аварийное восстановление в тестовую БД. Реальный охват X и корректность
курсорного продолжения нужно проверять по независимым данным.
