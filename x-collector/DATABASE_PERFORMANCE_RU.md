# Оптимизация PostgreSQL

Миграция `013_reply_performance.sql` добавляет индексы без изменения данных:

| Индекс | Запросы |
| --- | --- |
| reply_accounts_user / reply_campaigns_user / reply_lore_user | Списки ресурсов и tenant join по user_id |
| reply_examples_lore | Примеры RAG по lore_id и каскадное удаление |
| reply_drafts_campaign_queue | Очередь pending и статистика кампании |
| reply_rates_epoch INCLUDE(account_id,count) | Текущий UTC-день глобальных/аккаунтных квот без чтения всей истории |
| reply_alerts_dedup | Проверка повторного алерта за последние 10 минут |
| reply_alerts_feed | Последние алерты пользователя |

Существующий индекс `reply_drafts_queue(account_id,status,created_at)` сохранён: он обслуживает другой путь (аккаунт/публикация). Индексы ускоряют чтение, но увеличивают стоимость записи и место на диске. После перехода на реальные данные следует проверить использование через pg_stat_user_indexes и планы запросов.

Статистика аккаунта/кампании теперь использует конкретный WHERE без nullable OR и без лишнего JOIN, после обязательной проверки владельца. Общая статистика по пользователю сохраняет tenant join. Тесты проверяют результаты и запрет доступа другого пользователя.

Pool по умолчанию для отдельного worker снижен с 20 до 3, supervisor — до 2, Telegram — до 3. PG_POOL_MAX сохраняет явную настройку пользователя. Worker требует минимум две connections: одна удерживает advisory lock, другая выполняет запросы. Это уменьшает максимальный бюджет соединений для 10 workers с 200 до 30, а не обещает, что все connections будут открыты.

## Измерение

Тест создаёт отдельные 100 аккаунтов, 50 000 черновиков и 200 000 записей квот. Сравнивает `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` до и после двух ключевых индексов при одинаковых данных, проверяет выбранный индекс, одинаковое число строк и меньшую оценку planner cost. Время не используется как нестабильный pass/fail критерий.

Локально на PGlite:

| Запрос | Planner cost до → после | Обращения к shared buffers до → после |
| --- | --- | --- |
| Очередь кампании | 1415.49 → 33.61 | 661 → 4 |
| Последние 24 часа квот | 1765.87 → 1398.12 | 453 → 128 |

Это результаты fixture, не замер production. Тот же benchmark встроен в `npm run test:postgres` и CI PostgreSQL 16. Он удаляет тестовые индексы только внутри собственной уникальной схемы, затем восстанавливает миграцию. Тестовые данные удаляются вместе с этой схемой. Не запускайте интеграционную проверку с production URL.

## Применение

```bash
npm run migrate -- --status
# В предназначенной для collector БД, после проверки backup и окна обслуживания:
npm run migrate
```

На большой существующей базе обычный CREATE INDEX может задерживать записи. Миграция не выполняется автоматически в production. Для такой базы администратор может построить эти же индексы через CREATE INDEX CONCURRENTLY отдельными командами вне транзакции, проверить валидность индексов, затем запустить штатный migrate (IF NOT EXISTS). Здесь production база не изменялась.

Автоматическое удаление исторических черновиков, алертов и квот не включено: срок хранения должен быть выбран пользователем. Не запускайте VACUUM FULL ради профилактики. Нативные показатели CI и нагрузка живых сервисов оцениваются отдельно.

## PostgreSQL 16 в CI

Workflow run 37700644370 завершился успешно: typecheck, lint, 52 tests, build и test:postgres. Нативное измерение той же fixture:

| Запрос | Planner cost до → после | Shared buffers до → после | Execution time, один запуск |
| --- | --- | --- | --- |
| Очередь кампании | 1415.47 → 33.60 | 661 → 4 | 5.575 → 0.038 мс |
| Последние 24 часа квот | 3779.94 → 1404.96 | 1274 → 131 | 11.518 → 0.445 мс |

Числа времени зависят от cache, hardware и размера строк. Они не гарантируют такое же ускорение production. Проверка подтверждает использование индексов и снижение объёма чтения на данной выборке.
