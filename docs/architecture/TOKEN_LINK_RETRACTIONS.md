# ARCH-07a: временные связи mint, отзыв подтверждений и честная история

Реализация: draft PR #136 поверх #135 → #134 → #133. Это НЕ подтверждение работоспособности на пользовательской БД.

## Источники и ограничения

- TG сохраняет сообщения и кандидатов в собственной PostgreSQL. В новой ветке при смене **текста** или восстановлении после удаления публикует `token_links_invalidated`, а при soft-delete — отдельное событие с причиной `deleted`. Изменение только просмотров/репостов не отменяет подтверждение.
- Оба новых события требуют `TG_INTELLIGENCE_OUTBOX_ENABLED=true` и `TG_INTELLIGENCE_TOKEN_LINKS_ENABLED=true`; по умолчанию оба выключены. Исходные текст, сессия MTProto, cookie, ключи RPC и данные прокси в Outbox не попадают.
- TG RPC resolver блокирует конкретное сообщение на время подтверждения, чтобы не отправить старый текст с новым временем наблюдения после параллельного изменения.
- Для X контракт отзыва предусмотрен, но автоматический X emitter/валидатор RPC mint отсутствует. Не приравнивать совпадение адреса или ticker к on-chain proof.

## Данные Intelligence

Новая **дополнительная** миграция `intelligence/migrations/004_token_link_observations.sql` создаёт `token_link_observations` после миграции 001; миграции 001–003 не изменять. Эта таблица хранит события `token_link_verified` и `token_links_invalidated` неизменяемо.

`queryActiveTokenLinks(tokenId, occurredBefore, knownAt)` формирует ссылки, подтверждённые к заданному моменту, и исключает подтверждения, отозванные по тому же точному evidence ID. Отзыв действует на **все mint** в конкретном X/TG-сообщении, а не только один известный адрес. Новое подтверждение после отзыва может восстановить актуальную связь. При равных timestamp предпочитается безопасное исключение: проверка использует `invalidated.observed_at >= verified.observed_at`.

Существующий `queryTokenTimeline` **не изменён**. Отзывы и token-link assertions не превращаются в необратимые публикации в Timeline. Не выдавать два API за одно и не называть этот PR готовым Token Intelligence UI.

## Порядок безопасного развёртывания

1. Сначала backup + проверенное восстановление отдельных source/target PostgreSQL, отдельно WAL-aware SQLite для Blockchain.
2. Проверить все схемы на временных копиях. Применить **004** в отдельной Intelligence PostgreSQL до передачи событий `token_link_*`.
3. Проверить отсутствие несохранённых/старых ревизий, наличие stable X/TG IDs и даты публикации/наблюдения. Не генерировать post-hoc наблюдения для старых данных.
4. Запускать конечные ETL батчи на изолированных БД; проверить повторные доставки, инверсию порядка, поздний ACK, rollback и два временных cutoffs.
5. Лишь после проверок и явного разрешения оператора вручную включить source flags. Отказ от флагов останавливает новые link events, но не меняет историю.
6. Настроить независимый coverage/backfill: ссылки, подтверждённые до появления tombstone emitter, не могут считаться гарантированно актуальными без пересмотра полного контента/версии и статуса удаления.

## Известные границы

- X on-chain proof producer, Blockchain token resolver и POTAPoff unified API/UI НЕ готовы.
- Source-level edit/delete сообщает о потере актуальности с времени **наблюдения**, но не реконструирует задним числом события, произошедшие до включения нового outbox emitter.
- Новая связь после редактирования требует повторной квалифицированной on-chain проверки; простое совпадение тикера недостаточно.
- Данные `entity_evidence` сохраняются навсегда как историческое доказательство. Для «актуальных» токеновых привязок нужно использовать только `queryActiveTokenLinks` с временными cutoffs.
- Само наличие mint-аккаунта не означает отсутствие rug risk, торговую доходность или доказанное владение кошельком.
