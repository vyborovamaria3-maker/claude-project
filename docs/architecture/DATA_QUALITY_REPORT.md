# ARCH-09 — локальный отчёт о качестве данных

**Статус:** добавлен read-only отчёт `intelligence/scripts/quality.mjs`, планируется черновой PR поверх ARCH-08 (#139). Он не запускает XActions, Telegram Collector, Solana RPC, ETL-доставку или сервер и не меняет пользовательские базы.

## Какие проблемы обнаруживает

| Объект | Что реально измеряется | Чего метрика НЕ доказывает |
| --- | --- | --- |
| Каждый source Outbox | `total`, `pending`, `ready`, `leased`, `retryDelayed`, `deadLetter`, `processed`, возраст самого старого ожидающего события | Полноту всей истории источника, правильность проекции каждой версии, отсутствие потерянных событий |
| X-выборка | До 1000 последних сохранённых твитов по длине/ID; доля записей с числовым author ID и пригодной датой наблюдения | Число всех существовавших публикаций и точность token mint |
| TG-выборка | До 1000 последних по локальному source/message ID; наличие стабильного peer ID, корректной даты, пометка удаления | Исторические редакции, удалённые до начала сбора сообщения и всю непрерывность Telegram |
| Blockchain-выборка | До 1000 последних `chain_seed_events`; вид записи wallet, базовая структура address/signature, SHA-256 raw payload, дата наблюдения | Полный decoder, финальность, owner attribution, transfer/mint/burn, полноту истории или PnL |
| Intelligence (опционально) | `intelligence_inbox`, `timeline_events`, `entity_evidence` kind=token, и `token_link_observations` при наличии миграции 004 | Равенство с количеством исходных сообщений или актуальные подтверждённые mint-links без retraction-aware API |
| Backfill checkpoint (опционально) | Счётчики `visited/inserted/duplicates/excluded`, `boundedScanComplete`, строгая привязка к source и хешу БД | Гарантию полной истории до или после этого snapshot, отсутствие старых версий и удалений |

**Принцип:** в JSON всегда `historicalCompleteness: "unknown"`. Даже при `boundedScanComplete=true` это лишь проход через зафиксированный диапазон ключей и не является доказательством всех когда-либо существовавших событий.

## Запуск на ноутбуке (Windows PowerShell)

Укажите соединения только с выбранными локальными базами в секретных локальных переменных среды (не добавляйте DSN/прокси/RPC ключи в git). Из директории `intelligence`:

```powershell
# Отдельный источник — только SELECT (для SQLite - readonly=true)
npm run etl:quality -- --sources x --format table

# Все три источника при доступных настройках соединения:
npm run etl:quality -- --sources x,tg,blockchain --sample 200 --format table

# Отдельно запросить счётчики центральной Intelligence PostgreSQL:
npm run etl:quality -- --sources x,tg,blockchain --target --format json

# Добавить проверку checkpoint, связанного с той же исходной БД:
npm run etl:quality -- --sources x --checkpoint x=C:\temp\intelligence-backfill-x.json --format json

# Автоматический контроль: код завершения 2 при недоступности,
# dead-letter, просроченной очереди или плохой выборке:
npm run etl:quality -- --sources tg --strict --stale-minutes 60
```

Доступны `--sources` (одно/несколько из x,tg,blockchain), `--sample` (1..1000), `--stale-minutes` (1..1440), `--format json|table`, `--target`, `--strict`, `--checkpoint SOURCE=FILE` (можно повторить для независимых источников).

Для `--target` отдельно требуется `INTELLIGENCE_DATABASE_URL`. Отчёт предназначен для запросов и не применяет миграции; отсутствие схемы или связи выводится как `unavailable`, а не как нулевой backlog. Нельзя считать `status=observed` подтверждением 100% полноты истории: это означает лишь, что *измеренные* очереди и выборка не достигли заданных границ тревоги.

## Интерпретация порогов

- `observed`: выбранная БД прочитана, нет найденных dead-letter, очередь не старше порога, нет исключений в ограниченной выборке. Историческая полнота **всегда unknown**.
- `attention`: найден хотя бы один dead-letter, очередь старее `stale-minutes`, проблемный source snapshot в выборке, неконсистентные счётчики или неверный checkpoint.
- `unavailable`: не получена нужная база, отсутствует обязательная схема или невозможно исполнить запрос. Исходные исключения не выводятся: они могут содержать пароль/DSN/текст.
- Если `--target` не указан, целевая БД обозначается `not_requested`. Это **не** означает, что доставка целостна.
- `ready`, `leased`, `retryDelayed` могут частично пересекаться; эти числа нельзя суммировать и выдавать за `pending`.

## Безопасность и эксплуатация

- Для `blockchain` SQLite открывается в режиме readonly + `fileMustExist`. Для PostgreSQL используются `SELECT` и существующие конечные query timeout, без транзакций изменения.
- Ограниченные исходные выборки никогда не читают текст публикаций, cookie, TG session, API ключи или сырые transaction payload. Отчёт содержит только агрегаты, статусы и безопасные категории причин.
- Полный `COUNT` по source Outbox является намеренным запросом состояния очереди. На очень большой таблице оцените нагрузку на копии; этот отчёт не является непрерывным монитором.
- Checkpoint *не переиспользуйте* между базами; проверка использует хеш фактического идентификатора БД, но не переносит DSN в JSON.
- `--strict` полезен для **локального** контроля перед запуском новых ETL-батчей. Никаких автоматических фоновых заданий, отправки уведомлений или облачного мониторинга не создаётся.

## Проверки и дальнейший путь

- Pure unit: аргументы, пороги, выборочная пригодность, fail-closed checkpoint, редактирование строк отчёта.
- SQLite: in-memory Outbox, 1 кошелёк с валидной записью, возраст очереди, никакой записи.
- PostgreSQL: временные схемы X/TG и Intelligence; качество source snapshots, исключение удалённых TG, отсутствие искусственного `100% coverage`, состояние destination/миграции 004.
- Следующий шаг — проверяемое историческое покрытие, страничная сверка `source outbox event key ↔ destination inbox` с checkpoint по диапазонам, графики и безопасный API POTAPoff, а не объявление полноты только по агрегатам.
